IT SERVICE DESK TICKETING SYSTEM
TECHNICAL IMPLEMENTATION SPECIFICATION
Version 1.0
Prepared for L2 development
Date: 2026-09-17

IMPORTANT
---------
This document is the technical companion to:
"IT Service Desk Ticketing System - Functional and Technical Specification v1.0".

It describes the recommended Azure architecture, development stack,
Microsoft Graph integration, security model, implementation sequence,
and estimated monthly Azure cost.

The primary design objective is:
- secure
- maintainable by internal IT/L2
- low operating cost
- no unnecessary Azure services
- suitable for approximately 100 Requesters + 4 initial Admins
- expandable later without redesigning the core data model

2.1 AZURE APP SERVICE
---------------------

Purpose:
Hosts the web application and Node.js backend/API.

Recommended production starting tier:
App Service B1.

The F1 Free plan costs $0 but Microsoft explicitly describes F1 as
intended for trials, experimentation and learning; production workloads
are not supported and there is no SLA.

Therefore:
- F1 = acceptable for early development/testing only
- B1 = recommended production starting point

Microsoft currently lists B1 at approximately USD 54.75/month on the
Windows App Service pricing page.

Source:
https://azure.microsoft.com/pricing/details/app-service/


IMPORTANT COST OPTIMIZATION:
----------------------------
If the company already has an Azure App Service Plan with unused
capacity, the application may be deployed into that existing plan.
Then there may be no incremental App Service compute cost.

The developer must check the existing Azure subscription before creating
a new App Service Plan.


2.2 AZURE SQL
-------------

Create:
- one logical Azure SQL Server
- one database for the application

Recommended initial database:
Azure SQL Database Basic

Expected workload is very small:
- ~100 Requesters
- 4 initial Admins
- relatively low ticket volume
- small relational dataset

Basic is therefore appropriate for MVP if its performance is sufficient.

Alternative:
Azure SQL Database General Purpose Serverless if the company prefers
automatic scaling/auto-pause and the regional pricing makes it cheaper
or operationally preferable.

Do not start with:
- Managed Instance
- Hyperscale
- Premium
- large provisioned vCore configuration

Those would be unnecessary for this workload.

Microsoft documents that SQL Database serverless can automatically
scale compute and can auto-pause during inactivity in the General
Purpose tier.

Source:
https://azure.microsoft.com/pricing/details/azure-sql-database/

4.2 USER'S DEVICES
------------------

The application must retrieve the user's managed Intune devices.

Microsoft Graph Intune managedDevice endpoint:

GET
/deviceManagement/managedDevices

Microsoft documents the application permission:

DeviceManagementManagedDevices.Read.All

for read access to Intune managed devices.

Source:
https://learn.microsoft.com/en-us/graph/api/intune-devices-manageddevice-list


4.3 INTUNE PERMISSION
---------------------

Minimum intended application permission:

DeviceManagementManagedDevices.Read.All

This is an application permission and requires administrator consent.

Microsoft explicitly documents that this permission allows reading
Intune managed devices.

Do NOT request:
DeviceManagementManagedDevices.ReadWrite.All

because the ticketing application does not need to modify Intune
devices.

Do NOT request:
DeviceManagementManagedDevices.PrivilegedOperations.All

because the ticketing application must not perform remote device actions.

Source:
https://learn.microsoft.com/en-us/graph/permissions-reference


4.4 IMPORTANT GRAPH SECURITY RULE
---------------------------------

The ticketing application is READ-ONLY with respect to Intune.

It must never:
- wipe device
- retire device
- reboot device
- reset passcode
- locate device
- modify device properties
- modify Intune configuration

The application only retrieves information.


4.5 DEVICE DATA

Do not assume that an IP address is always available in the
managedDevice resource.

======================================================================
7. TICKET NUMBER GENERATION
======================================================================

Format:

TCK-2026-0000001

Do not generate the ticket number in the browser.

The backend/database must generate it.

Recommended approach:
- maintain a database sequence or controlled counter
- perform ticket creation in a transaction
- guarantee uniqueness with a unique database constraint

Recommended SQL constraint:

UNIQUE(ticketNumber)

The ticket ID and ticket number are different:
- id = internal database key
- ticketNumber = user-facing identifier


======================================================================
8. TICKET CREATION TRANSACTION
======================================================================

When a Requester creates a ticket:

1. Authenticate user.
2. Determine Entra Object ID.
3. Load/create local Users record.
4. Validate subject.
5. Validate description.
6. Validate category/subcategory.
7. Validate priority.
8. Validate selected device.
9. If device is selected, retrieve current device data.
10. Create ticket.
11. Generate unique TCK number.
12. Create device snapshot.
13. Create AuditLog entry.
14. Create notification event.
15. Commit transaction.
16. Return ticket.

Email sending should NOT occur synchronously inside the database
transaction.


======================================================================
9. ASSIGNMENT IMPLEMENTATION
======================================================================

Ticket fields:

assignedTeamId
assignedUserId

Rules:

assignedTeamId = NULL
assignedUserId = NULL
=> Unassigned

assignedTeamId = SD
assignedUserId = NULL
=> SD queue

assignedTeamId = SD
assignedUserId = Orsi
=> SD / Orsi

If assignedUserId is not NULL:
- assigned user must be an active Admin
- assigned user's team should normally match assignedTeamId

Cross-team transfer:

assignedTeamId = L2
assignedUserId = NULL

Then an L2 Admin can take ownership:

assignedUserId = L2 Admin


======================================================================
10. STATUS AND PROGRESS
======================================================================

Status enum:

NEW
ASSIGNED
IN_PROGRESS
WAITING_FOR_USER
WAITING_FOR_THIRD_PARTY
RESOLVED
CLOSED

No CANCELLED.

Progress calculation:

NEW                    0
ASSIGNED               10
IN_PROGRESS            50
WAITING_FOR_USER       50
WAITING_FOR_THIRD_PARTY 50
RESOLVED               90
CLOSED                 100

Implement as a function/mapping in backend/frontend shared logic.

Do not allow the client to submit arbitrary progress.


======================================================================
11. RESOLVED -> CLOSED AUTOMATION
======================================================================

When Admin sets:

status = RESOLVED

Backend:
resolvedAt = current timestamp
autoCloseAt = current timestamp + 5 days

Azure Function runs periodically.

Example schedule:
every 15 minutes

Query:
status = RESOLVED
AND autoCloseAt <= current timestamp

For each matching ticket:

1. Start transaction.
2. Re-read ticket.
3. Confirm it is still RESOLVED.
4. Confirm autoCloseAt <= now.
5. Set status = CLOSED.
6. Set closedAt = now.
7. Create AuditLog with actor = SYSTEM.
8. Create requester notification.
9. Commit.


======================================================================
12. RESOLVED COMMENT TIMER RESET
======================================================================

If Requester comments on a Resolved ticket:

1. Save comment.
2. Keep status = RESOLVED.
3. Set autoCloseAt = current timestamp + 5 days.
4. Create audit log.
5. Create notification for assigned Admin/team.

Do NOT automatically set status back to In Progress.

15. ATTACHMENT IMPLEMENTATION
======================================================================

Frontend:
multipart/form-data upload to backend.

Backend:
1. authenticate user
2. authorize ticket access
3. validate file extension
4. validate MIME type
5. validate size
6. generate safe storage name
7. upload to private Blob container
8. save attachment metadata in SQL
9. audit log

Never use the original filename as the storage object key.

Recommended storage key:

tickets/{ticketId}/{guid}-{safeExtension}

Example:

tickets/8a7.../3e4...-pdf


DOWNLOAD
--------

Do not expose the Blob container publicly.

Backend can:
- authorize access
- generate a short-lived SAS URL
OR
- stream/download the blob through an authorized backend endpoint

For a small internal application, a short-lived authorized download is
reasonable.

16. WORKLOG IMPLEMENTATION
======================================================================

- maximum 20 lines

This is an implementation safeguard and can be adjusted later.

======================================================================
25. RELIABILITY REQUIREMENTS
======================================================================

Ticket creation must be transactional.

A ticket must never exist without:
- valid requester
- valid ticket number
- valid status
- valid priority

Where device snapshot creation fails because Graph is unavailable,
ticket creation may continue, but the failure must be recorded.

Notification failure must never roll back a successful ticket change.

Automatic closure must be idempotent.


======================================================================
26. GRAPH FAILURE STRATEGY
======================================================================

If Graph is unavailable:

Requester sees:
"Device information is temporarily unavailable."

The user can select:
Other device

The ticket can still be created.

Backend logs:
GRAPH_DEVICE_LOOKUP_FAILED

Do not retry Graph synchronously many times during a user request.

Use:
- short timeout
- limited retry
- graceful fallback

- retention period
- restore capability
- point-in-time restore
- company's Azure backup requirements

Do not build a custom backup system for MVP.


======================================================================
28. STORAGE BACKUP / RETENTION
======================================================================

Attachments are potentially business data.

The developer should confirm the company's retention requirements.

For MVP:
- private Blob Storage
- appropriate redundancy
- no public access

Do not automatically delete ticket attachments when a ticket closes.


======================================================================
29. DOMAIN / NETWORKING
======================================================================

Initial MVP does not require:
- Azure Front Door
- Application Gateway
- API Management
- private VNet
- private endpoint for every service

These would add cost and complexity.

The application can initially use:
HTTPS
+
App Service
+
Azure SQL firewall rules
+
Managed Identity
+
private Blob container
+
Entra authentication

If company security policy requires private endpoints/VNet integration,
that becomes a later architecture/security requirement.


======================================================================
30. API MANAGEMENT
======================================================================

DO NOT deploy Azure API Management for MVP.

Reason:
- unnecessary cost
- unnecessary complexity
- only one internal application/API
- no external API consumers

The App Service backend is sufficient.


======================================================================
31. REDIS / CACHE
======================================================================

DO NOT deploy Azure Cache for Redis for MVP.

The workload is too small to justify it.

If later required:
- category caching
- dashboard caching
- Graph result caching

can be implemented in application memory first.


======================================================================
32. SERVICE BUS
======================================================================

DO NOT deploy Azure Service Bus for MVP unless notification volume or
workflow complexity requires it.

The initial notification queue can be implemented with:
- SQL Notifications table
- Azure Function polling

This avoids an additional paid service.

If later the application requires high reliability/event volume, Service
Bus can replace the SQL polling mechanism.

33. EMAIL IMPLEMENTATION COST
======================================================================

If Microsoft Graph SendMail is used with the company's existing
Exchange Online/Microsoft 365 tenant, there is normally no separate
per-email Azure service required.

The company must already have the appropriate Microsoft 365/Exchange
licensing and mailbox/service-account arrangement.

Do not introduce SendGrid or another paid email provider unless company
policy requires it.

======================================================================
36. COST-SAVING RULES
======================================================================

DO:
- reuse existing Azure resources where appropriate
- use App Service B1 for production instead of larger tiers
- use Functions Consumption/Flex Consumption
- use Azure SQL Basic initially
- use Blob Storage LRS
- use Managed Identity
- keep Application Insights logging controlled
- avoid API Management
- avoid Redis
- avoid Service Bus initially
- avoid Front Door initially
- avoid unnecessary Key Vault secrets

DO NOT:
- use Premium SQL
- use Premium Functions
- use multiple App Service instances initially
- use dedicated notification infrastructure
- create unnecessary VMs
- store attachments in SQL

The following are considered mandatory even on a low budget:

- Entra authentication
- HTTPS
- server-side authorization
- Managed Identity
- private Blob container
- least-privilege Graph permissions
- read-only Intune access
- SQL parameterization
- server-side upload validation
- audit logging
- Application Insights
- secure configuration
- no secrets in source control

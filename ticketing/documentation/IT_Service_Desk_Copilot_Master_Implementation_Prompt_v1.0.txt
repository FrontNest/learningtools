======================================================================
1. PRIMARY OBJECTIVE
======================================================================

Build a small, secure, maintainable internal Service Desk application
for approximately:

- 100 Requesters
- 2 SD Admins
- 2 L2 Admins
- approximately 20 Requester teams

The application runs on Azure.

Required main architecture:

- React frontend
- Node.js + TypeScript + Express backend/API
- Azure App Service
- Azure SQL Database
- Azure Blob Storage for attachments
- Azure Functions for background processing
- Microsoft Entra ID for authentication
- Microsoft Graph for Entra/Intune data
- Application Insights / Azure Monitor
- Managed Identity where supported

The application is NOT intended to be a full ITIL/ITSM platform.

2. NON-NEGOTIABLE FUNCTIONAL REQUIREMENTS
======================================================================

Ticket number:

TCK-YYYY-NNNNNNN

Example:

TCK-2026-0000001

There is NO Cancelled status.

Allowed statuses:

NEW
ASSIGNED
IN_PROGRESS
WAITING_FOR_USER
WAITING_FOR_THIRD_PARTY
RESOLVED
CLOSED

Progress is derived from status:

NEW                     0%
ASSIGNED               10%
IN_PROGRESS            50%
WAITING_FOR_USER       50%
WAITING_FOR_THIRD_PARTY 50%
RESOLVED               90%
CLOSED                100%

Do not allow users to set arbitrary progress values.

6. DEVICE INFORMATION
======================================================================

The system must present the Requester's managed devices from
Microsoft Graph / Intune.

The Requester selects the affected device.

There must also be:

OTHER DEVICE

If selected, allow manual device description/identifier.

The selected device's relevant information must be captured in a
Ticket Device Snapshot at ticket creation.

Do not rely only on the current Intune state because the device may
change later.

Potential device fields include:

- device name
- Entra device ID
- Intune managed device ID
- serial number
- manufacturer
- model
- operating system
- OS version
- compliance state
- management state
- last check-in
- IP address if actually available from the API

Never assume that every Graph/Intune field is available.

If Graph device lookup fails, ticket creation must still be possible
using Other Device.

7. MICROSOFT GRAPH
======================================================================

Use Microsoft Graph REST API.

Base:

https://graph.microsoft.com/v1.0

The backend, not the browser, must perform privileged Graph access.

The intended Intune permission is:

DeviceManagementManagedDevices.Read.All

Do NOT request:

DeviceManagementManagedDevices.ReadWrite.All

Do NOT request privileged remote-operation permissions.

The ticketing system is READ-ONLY with respect to Intune.

Never:
- wipe devices
- retire devices
- modify devices
- reboot devices
- reset passcodes
- perform remote Intune actions

Use least privilege.

10. STATUS WORKFLOW
======================================================================

Normal lifecycle:

NEW
 ->
ASSIGNED
 ->
IN_PROGRESS
 ->
WAITING_FOR_USER
 ->
IN_PROGRESS
 ->
RESOLVED
 ->

WAITING_FOR_THIRD_PARTY -> IN_PROGRESS

Admins may perform appropriate status changes.

Requesters cannot set RESOLVED or CLOSED.


======================================================================
11. RESOLVED -> CLOSED AUTOMATION
======================================================================

When an Admin changes a ticket to RESOLVED:

resolvedAt = current timestamp

autoCloseAt = current timestamp + 5 days

The ticket remains RESOLVED during this period.

An Azure Function must periodically find:

status = RESOLVED
AND autoCloseAt <= current timestamp

and change the ticket to:

CLOSED

Set:

closedAt = current timestamp

Create an AuditLog entry with actor:

SYSTEM

Reason:

Automatic closure after 5 days.

The operation must be idempotent.


======================================================================
12. REQUESTER COMMENT ON RESOLVED TICKET
======================================================================

If a Requester comments while the ticket is RESOLVED:

- keep status = RESOLVED
- reset autoCloseAt to comment timestamp + 5 days
- notify the assigned Admin/team
- create AuditLog entry

DO NOT automatically reopen the ticket.

Example:

Resolved:
17 Sep

Requester comment:
19 Sep

New autoCloseAt:
24 Sep


======================================================================
13. MANUAL CLOSURE
======================================================================

An Admin may close a RESOLVED ticket before the 5-day period expires.

Example:

Requester:
"The problem is solved."

Admin:

RESOLVED -> CLOSED

Create AuditLog entry.


======================================================================
14. COMMENTS
======================================================================

Two comment types:

PUBLIC
INTERNAL

PUBLIC:
- visible to Requester and Admins

INTERNAL:
- visible only to Admins

Requesters may create PUBLIC comments only.

Admins may create PUBLIC and INTERNAL comments.

Comments should be append-only for MVP.

15. WORKLOG

- ticket

The browser-side validation must never be considered sufficient.

34. NOTIFICATION RELIABILITY
======================================================================

Notification processing must be retryable.

Notification statuses:

PENDING
SENT
FAILED

A failed notification should contain an error message suitable for
administrative troubleshooting, but must not contain credentials or
tokens.

Use controlled retry/backoff.

Do not create infinite retry loops.


======================================================================
35. AUTO-CLOSE RELIABILITY
======================================================================

The auto-close Function must be safe if executed multiple times.

Before closing:

- reload ticket
- verify status == RESOLVED
- verify autoCloseAt <= now

Then close.

This avoids closing a ticket that was changed by an Admin between the
initial query and update.
